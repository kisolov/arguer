# arguer: почему сделано так

Дайджест решений в формате «решение / альтернативы / почему». Полные спеки и планы лежат локально в `docs/superpowers/specs/` и `docs/superpowers/plans/`; эта папка исключена из git, поэтому ссылок на них нет, названия файлов даны для поиска на машине автора.

Как устроено сейчас — в [ARCHITECTURE.md](ARCHITECTURE.md), правила и формулы — в [INVARIANTS.md](INVARIANTS.md).

## 1. Языковая модель за узким портом

| | |
|---|---|
| **Решение** | `LanguageModelInterface.complete(messages) -> str`, при сбое `LanguageModelError`. Адаптер [GenAPIClient](../../../src/infrastructure/genapi.py) разбирает ответ провайдера сам |
| **Альтернативы** | вернуть из порта сырой JSON провайдера и разбирать его в домене; вернуть структуру с метаданными (токены, модель) |
| **Почему** | раньше порт передавал лишние данные в избыточном формате. Домену нужен только текст ответа, а формат GenAPI остаётся знанием адаптера |

## 2. Async SQLAlchemy 2.0 вместо Pony ORM

| | |
|---|---|
| **Решение** | Асинхронный SQLAlchemy (`AsyncSession`, `async_sessionmaker(expire_on_commit=False)`), драйверы `aiomysql` в проде и `aiosqlite` в тестах |
| **Альтернативы** | оставить Pony (синхронный); синхронный SQLAlchemy в `asyncio.to_thread` |
| **Почему** | синхронные вызовы Pony блокировали event loop бота; SQLAlchemy 2.0 — стандартный стек, его ожидают увидеть в проекте. Синхронный SQLAlchemy в потоках убрал бы блокировку цикла, но оставил бы прежний стек без async-транзакций |
| **Спека** | `2026-09-29-sqlalchemy-async-migration-design.md` |

Следствия: порты репозиториев асинхронные; `Transaction.user` грузится явно, а `relationship(lazy="raise")` превращает забытую загрузку в мгновенную ошибку (lazy-load в async невозможен).

## 3. Формат данных совместим со старыми таблицами

| | |
|---|---|
| **Решение** | Enum'ы — VARCHAR(255) со значениями `.value` (`values_callable`, `native_enum=False`, без CHECK); FK-колонка называется `user`; вещественные поля — `Double` |
| **Альтернативы** | нативный `ENUM`; колонка `user_id`; `Float` |
| **Почему** | боевые таблицы уже созданы прежней ORM с таким форматом, а Alembic в проекте нет. Переименование колонки или смена типов потребовали бы ручной миграции на живой БД. `Float` на MySQL — одинарная точность, для баланса недопустимо |

## 4. Alembic не подключён

| | |
|---|---|
| **Решение** | Схему создаёт `create_all` при старте; изменения существующей БД — ручные SQL-файлы в [sql/](../../../sql/) |
| **Альтернативы** | Alembic с версионированием |
| **Почему** | схема из двух таблиц, миграций до сих пор не требовалось. **Цена:** `create_all` не добавляет индексы и колонки в существующие таблицы, каждая следующая смена схемы на боевой БД — ручная работа (см. [001](../../../sql/001_users_unique_telegram_id.sql)) |

## 5. Баланс: атомарный UPDATE, а не «прочитал-изменил-записал»

| | |
|---|---|
| **Решение** | `change_balance(user_id, delta)` — один условный `UPDATE ... SET bal = bal + :delta WHERE bal + :delta >= 0`; проверка «не уйти в минус» и изменение неразделимы |
| **Альтернативы** | читать `User`, менять `bal` в памяти, писать через `store` (так было); `SELECT ... FOR UPDATE`; версионный столбец с оптимистичной блокировкой |
| **Почему** | снимок в памяти терял обновления: два начисления за одно «обновить» давали 350 вместо 450, параллельные списания могли увести баланс в минус. `FOR UPDATE` удерживал бы блокировку строки на время `await`-ов между запросами; версионный столбец потребовал бы повторов и миграции схемы. Условный `UPDATE` работает одинаково на MySQL и sqlite и не требует ни блокировок, ни изменения схемы |
| **Спека** | `2026-09-29-billing-uow-and-review-fixes-design.md` |

## 6. Unit of Work для биллинга

| | |
|---|---|
| **Решение** | Порт [UnitOfWork](../../../src/domain/ports/unit_of_work.py) (`async with`, коммит при выходе без исключения, откат при исключении); [SqlUnitOfWork](../../../src/infrastructure/db/unit_of_work.py) держит одну сессию и транзакцию, репозитории привязываются к ней. В DI — `Factory`, `BillingService` получает `unit_of_work.provider` |
| **Альтернативы** | два независимых коммита (транзакция, затем баланс) — как было; общая долгоживущая сессия на репозиторий; ручной `session.begin()` в сервисе |
| **Почему** | два коммита оставляли окно, в котором сбой давал баланс без записи транзакции или наоборот. Порт с контекстным менеджером не пускает `AsyncSession` в домен. Экземпляр на сценарий, потому что у сценария своя транзакция; поэтому `Factory`, а не `Singleton` |

Отмена (`cancel_transaction`) осталась вне UnitOfWork: это одна запись без связанных изменений.

## 7. Compare-and-set для смены статуса транзакции

| | |
|---|---|
| **Решение** | `transition_pending(id, status)` — `UPDATE ... WHERE id = :id AND status = 'pending'`, успех определяется по `rowcount == 1` |
| **Альтернативы** | читать статус и проверять в коде; уникальный ключ на платёж |
| **Почему** | проверка в коде оставляла гонку: два параллельных «обновить» видели `PENDING` и оба начисляли. CAS выбирает победителя в БД; проигравший ничего не начисляет и читает итоговое состояние |

## 8. Регистрация пользователя: замок и уникальный индекс

| | |
|---|---|
| **Решение** | `get_or_create` в [SqlUserRepository](../../../src/infrastructure/db/repositories/user.py): `asyncio.Lock` в процессе, уникальный индекс `ix_users_telegram_id` между процессами, проигравший ловит `IntegrityError` и перечитывает |
| **Альтернативы** | только индекс; только замок; `INSERT ... ON DUPLICATE KEY UPDATE` |
| **Почему** | после перехода на async пачка пересланных сообщений от нового пользователя обрабатывается параллельно, и это порождало дубли (воспроизведено тестом: четыре записи). Индекс надёжен, но в существующей БД его нет до ручной миграции, замок закрывает этот период. `ON DUPLICATE KEY` — синтаксис MySQL, а тесты идут на sqlite |

## 9. `Database` — Singleton, а не Resource

| | |
|---|---|
| **Решение** | В [di.py](../../../di.py) `Database` объявлен `providers.Singleton`; закрывает engine `main()` в `finally` |
| **Альтернативы** | `providers.Resource` с init/shutdown |
| **Почему** | engine создаётся лениво и без I/O. `Resource` вне async-контекста возвращает незавершённый `Future` вместо объекта, что даёт трудноуловимые ошибки при разрешении цепочки провайдеров |

## 10. Пополнение подтверждается по кнопке

| | |
|---|---|
| **Решение** | Баланс пополняется, когда пользователь нажимает 🔄: бот спрашивает YooKassa о статусе `PENDING`-транзакций |
| **Альтернативы** | вебхук YooKassa; фоновый опрос по расписанию |
| **Почему (по структуре кода)** | у процесса нет входящего HTTP-сервера, только long polling Telegram; вебхук потребовал бы публичного адреса и проверки подписи. **Цена:** оплаченный, но необновлённый платёж не зачисляется, пока пользователь сам не нажмёт кнопку |

## 11. FSM в Redis и очередь апдейтов пользователя

| | |
|---|---|
| **Решение** | `Dispatcher(storage=RedisStorage, events_isolation=SimpleEventIsolation())` в [di.py](../../../di.py); значения FSM сериализуются pickle + base64 ([fsm_storage.py](../../../src/infrastructure/aiogram/fsm_storage.py)) |
| **Альтернативы** | оставить FSM в памяти; Redis без изоляции; свой замок «идёт /go» в `Go` |
| **Почему** | в памяти контекст терялся при каждом деплое. Redis без изоляции превращает `update_data` в чтение и запись через сеть, и пачка пересланных сообщений теряла бы часть из них. Параллельные апдейты одного пользователя давали и двойной `/go` с двумя списаниями: `processing` ставился после списания, а между ними шли запросы к БД. Изоляция закрывает всё это одним механизмом aiogram, свой замок закрыл бы только `/go`. json не умеет доменные объекты контекста. **Цена:** пока идёт `/go`, остальные апдейты этого пользователя ждут |

## 12. /go возвращает списание, если ответ не дошёл

| | |
|---|---|
| **Решение** | [Go](../../../src/application/uc/go.py): `processing` до списания, сброс в `finally`; сбой после списания и до отправки ответа → транзакция `REFUND` и восстановление контекста |
| **Альтернативы** | списывать после ответа модели; резервировать сумму и подтверждать списание после ответа |
| **Почему** | раньше сбой модели оставлял пользователя без денег и без ответа, а состояние `processing` не снималось, и бот молчал до перезапуска. Списание после ответа позволило бы получить ответ при нехватке средств между проверкой и списанием. Резерв потребовал бы нового статуса и миграции. Возврат — отдельная запись, поэтому история списаний не переписывается |

## 13. Пополнение записывается до создания платежа

| | |
|---|---|
| **Решение** | [SendPaymentLink](../../../src/application/uc/send_payment_link.py): `open_top_up` (PENDING без `uuid`) → `create_payment` → `attach_payment` → ссылка. Ошибка YooKassa отменяет запись |
| **Альтернативы** | прежний порядок «платёж → запись»; ключ идемпотентности от id транзакции и повтор `create_payment` |
| **Почему** | при прежнем порядке сбой БД после создания платежа оставлял платёж без записи. Теперь ссылка уходит только после привязки `uuid`, поэтому оплатить можно только платёж, о котором знает БД. Повтор по ключу идемпотентности не нужен: без ссылки неоплаченный платёж просто истекает |

## Открытые вопросы, не решения

Не выбранные альтернативы, а места, где решение не принималось: списание при падении процесса посреди `/go` не возвращается; очередь апдейтов пользователя локальна процессу, поэтому несколько экземпляров бота не поддерживаются (см. [FAILURE_MODES.md](FAILURE_MODES.md)). Здесь они отмечены, чтобы не читались как намеренный выбор.
