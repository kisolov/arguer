# arguer: поведение при сбоях

Описано как есть, включая нежелательное. Исправления здесь не обсуждаются: это отражение кода, а не план работ. Общая схема: исключение из юзкейса доходит до [ErrorHandlingMiddleware](../../../src/presentation/aiogram/error_handling.py).

| Тип исключения | Реакция middleware |
|---|---|
| `BusinessLogicError` | пользователю уходит текст исключения; контекст и **состояние не сбрасываются** |
| любое другое | лог `Неожиданная ошибка` с трассой, пользователю «Ошибка! Обратитесь в техподдержку», **сбрасываются весь контекст (`clear_data`) и состояние** |
| ошибка при отправке самого сообщения об ошибке | уходит в aiogram Dispatcher, который её логирует |

## Сценарии

### А. Модель не ответила во время /go

Порядок в [go.py](../../../src/application/uc/go.py): состояние `processing` → списание → распознавание → запрос к модели → отправка ответа. Сбой на любом шаге после списания и до отправки ответа обрабатывается одинаково.

| Что | Итог |
|---|---|
| Баланс | списание возвращается отдельной транзакцией `REFUND`, пользователю уходит «Запрос не обработан, N✨ возвращены на баланс». Если сам возврат упал — лог `Не удалось вернуть списание` с id транзакции, наружу уходит исходная ошибка |
| Сообщение «Идёт обработка...» | удаляется (`finally`) |
| Контекст | восстанавливается как до `/go`: `unprocessed`, `defendant` и прежний `processed`. `/go` можно повторить |
| Состояние | сбрасывается (`finally` в `Go`) |

### Б. Распознавание речи не удалось во время /go

| Что | Итог |
|---|---|
| Баланс | возвращается, как в сценарии А |
| Сообщение «Идёт обработка...» | удаляется (`finally`) |
| Контекст и состояние | `Go` восстанавливает контекст, но исключение неожиданное, и middleware затем сбрасывает весь контекст (`clear_data`): накопленная переписка потеряна, переслать её нужно заново |

### В. Недостаточно средств

`InsufficientFunds` бросается атомарным `UPDATE` внутри UnitOfWork на шаге списания; состояние `processing`, поставленное перед ним, снимается в `finally`. Записи транзакции нет, баланс не изменён, контекст остаётся; пользователь видит «Не хватает токенов! Пополнить баланс - /bal».

### Г. Сбой между двумя записями биллинга

Баланс и запись транзакции пишутся в одном UnitOfWork. Ошибка на записи транзакции откатывает и баланс; наружу уходит исходное исключение.

### Д. Параллельная обработка одной транзакции

Два одновременных «обновить»: `transition_pending` выигрывает один, второй читает уже проставленные статус и баланс и ничего не начисляет.

### Е. Повторные апдейты одного пользователя

Двойной `/go`, двойной тап по кнопке подзащитного, пачка пересланных сообщений: Dispatcher с `SimpleEventIsolation` обрабатывает апдейты одного пользователя по очереди. Второй `/go` начинается после первого и видит пустой `unprocessed` → `ContextEmpty`, второго списания нет. Пересланные сообщения дописываются в контекст по одному и не теряются. Цена: пока идёт `/go`, остальные апдейты этого пользователя ждут; апдейты других пользователей не ждут.

### Ж. Процесс упал посреди /go

Контекст и состояние лежат в Redis и переживают перезапуск, поэтому состояние может остаться `processing`. `/start` и `/clear` зарегистрированы до `processing_input_protection` и работают в нём: `/clear` сбрасывает зависшее состояние. Списание при таком падении не возвращается.

### З. Падение на старте

| Что падает | Итог |
|---|---|
| `create_schema` (БД недоступна) | исключение из `main`, `finally` закрывает engine; процесс завершается |
| первый выпуск IAM-токена (`yc`, Redis) | исключение из `refresh_token_and_schedule` до polling; процесс завершается |
| регулярное обновление токена (раз в 30 минут) | исключение в потоке APScheduler логируется планировщиком, бот продолжает работать. Ключ в Redis живёт 3600 с, поэтому одно пропущенное обновление токен не теряет; два подряд — теряет |

## Блокировка event loop

Синхронные вызовы и где они выполняются:

| Вызов | Где выполняется |
|---|---|
| чтение IAM-токена из Redis (синхронный клиент) при распознавании | `asyncio.to_thread` в [speechkit.py](../../../src/infrastructure/yandex/s3/speechkit.py) `_auth_header` |
| запись токена в Redis | поток планировщика и старт, до polling |
| конвертация видео pydub/ffmpeg | `asyncio.to_thread` в [web.py](../../../src/infrastructure/web.py) `_convert_video_sync` |
| `subprocess.run` для `yc` | [cloud_cli.py](../../../src/infrastructure/yandex/cloud_cli.py): поток планировщика и один раз при старте, на апдейты не влияет |

Тоже в потоках (`asyncio.to_thread`): GenAPI (`requests`, включая паузы между повторами), YooKassa SDK, boto3.

## Известные несоответствия

| Что | Состояние |
|---|---|
| Ключ идемпотентности YooKassa генерируется заново на каждый вызов | повтор `create_payment` = второй платёж. Сам бот `create_payment` не повторяет, а ссылка уходит только после записи платежа в БД (сценарий в [DESIGN.md](DESIGN.md) §13) |
| Форма тела запроса SpeechKit (`config.specification`) сверена с документацией API v2, но не с живым сервисом: тесты подменяют HTTP | до исправления блок был вложен дважды (`config.specification.specification`) |
